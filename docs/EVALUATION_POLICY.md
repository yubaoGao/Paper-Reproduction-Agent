# Evaluation Policy and Canonical Final Result

`EvaluationPolicy` is the execution-time truth for how a selected paper experiment obtains its final result. It records checkpoint policy, metric/split/direction, reporting split/metrics, run or seed count, aggregation, source, evidence, confidence and warnings. `UNKNOWN` is preserved; paper- or code-explicit policies require evidence. A marked `SCIENTIFIC_DEFAULT` must carry a warning.

Task 05 extracts only paper-explicit rules. Task 06 records explicit repository behavior as `RepositoryEvaluationPolicyRecord`, including bounded train/evaluation command references without introducing stdout/JSON/CSV/TensorBoard format models. Task 07 produces `EvaluationPolicyAlignment`. If paper policy is unknown, one explicit code policy may be used as `CODE_FALLBACK`. If both sources are unknown, a deterministic scientific default is created only when the paper supplies one unambiguous reporting split and metric set: `FINAL_EPOCH`, `source=SCIENTIFIC_DEFAULT`, `confidence=INFERRED`, and warning `INFERRED_EVALUATION_POLICY`. This rule never maximizes test epochs. Missing or ambiguous reporting information remains `UNKNOWN` and Task 08 blocks.

Paper/code disagreement such as best validation F1 versus best test F1 becomes `EVALUATION_POLICY_CONFLICT`, but the paper-explicit policy remains authoritative. The alignment records `REPOSITORY_EVALUATION_DEVIATION`. Task 08 proceeds only when Task 06 provides an evidenced explicit evaluation command that supports deterministic paper-policy adaptation inside the sandbox; otherwise it blocks with `repository_evaluation_deviation_not_adaptable`. It never silently executes the conflicting code policy.

Task 08 expands each resolved policy into a small `ExperimentActionPlan`: `TRAIN`, optional `EVALUATE`, and `AGGREGATE`. Task 11 admits these actions into its existing DAG/state machine. Multi-run plans resolve every run independently before deterministic mean or mean/std aggregation; no best-seed operation exists.

Repository-specific `RepositoryResultAdapter` implementations interpret bounded sandbox output and return structured `RunFinalResult` values. `CanonicalResultResolver` validates them and creates `FinalResult`. Core models do not contain file-format selectors. Direct dependency artifacts, including a TRAIN checkpoint reference, are included in the EVALUATE resolution request. Every run and final metric must retain artifact evidence or provenance, and every per-run reporting metric is bound to the run's selected checkpoint or epoch. An adapter cannot combine Accuracy and F1 from different checkpoints, change the selected paper experiment, change the locked policy, omit configured seeds, or substitute test-metric maximization for a validation selection rule.

Command success and reproduction success are separate. For an action that requires a canonical result, exit code zero is followed by deterministic FinalResult resolution. Missing or invalid FinalResult is a validation failure, and semantic/LLM validation is not called first.

Real Linux verification of checkpoint persistence/remounting between action sandboxes, repository-specific seed binding wrappers, and result adapters remains in the deployment integration phase.
